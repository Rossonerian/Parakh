# Testing troubleshooting

1. `./test doctor` and inspect the newest ignored `test-results/<run>/results.json` and `results.xml`. Exit nonzero may mean FAIL (a tested assertion) or BLOCKED (missing environment/evidence). Do not make a blocked stage green by removing it.
2. **Wrong Karmi branch:** `parakh-shadow-integration` contains the Karmi ↔ Parakh exchange and local `readiness-harness` adds the device/production-config probes; `main` has neither. Inspect `git branch --show-current` and candidate SHA in the manifest. Use the exact reviewed branch; no checkout/reset is performed automatically by `./test`.
3. **Python not found:** Parakh needs an isolated `.venv` from `pip install -e '.[dev]'`; Karmi needs Python >=3.12 and `pip install -c requirements.lock -e '.[dev]'`. Do not use the system interpreter if its dependencies do not match. Parakh's demo writes to a fresh per-run directory, never to an existing user-owned DB.
4. **No container engine / port busy:** with Docker, Karmi `scripts/tasks.py test-integration` uses its Compose file; without Docker the runner uses rootless Podman (`podman info`) with the same images, credentials and loopback ports. If `127.0.0.1:55432` or `:56379` is already bound, the stage is BLOCKED and nothing is stopped: find the owner with `ss -ltnp` and free it yourself. Leftover runner containers are named `parakh-readiness-*` (`podman ps -a --filter name=parakh-readiness`). Do not point the tests at a real/shared database or remove unrelated volumes.
5. **Flutter unavailable:** install the pinned Flutter 3.47.5, Android SDK and JDK17; run `flutter doctor -v`, `flutter pub get` in `Karmi/mobile`, then rebuild/debug-install this checkout. An old installed package is not candidate evidence. Physical device requires exactly one authorized USB device; `adb devices -l` status must be `device`. On unauthorized status approve USB debugging on the phone; on multiple devices disconnect the others or isolate them before evidence collection.
6. **Phone cannot reach backend:** backend must listen at `127.0.0.1:8000` when using `adb reverse tcp:8000 tcp:8000`; inspect `adb reverse --list`. Check `/ready` (DB), not just `/health` (liveness). Native Flutter needs a build-time `API_BASE_URL=http://127.0.0.1:8000` for USB reverse; the Android emulator instead defaults to `10.0.2.2`. Do not modify Android release cleartext policy to work around a local dev issue. See `docs/MOBILE_TESTING.md` for constrained LAN testing.
7. **APK mismatch:** `--drive` rebuilds and reinstalls the committed candidate automatically. With `--mobile-evidence`, `Karmi/mobile/build/app/outputs/flutter-apk/app-debug.apk` must hash to the same value as the installed `base.apk`. Rebuild and reinstall; never edit the evidence JSON.
   - **`INSTALL_FAILED_UPDATE_INCOMPATIBLE`:** the phone holds a Karmi build signed with another key. Uninstalling (`adb uninstall ai.karmi.app`) deletes that app's data, so only do it with the owner's approval.
   - **`127.0.0.1:8000 is in use`:** stop your own dev server (`ss -ltnp | grep ':8000 '`). The driver never reuses or kills it.
   - **A step times out waiting for a label:** keep the phone unlocked with its screen on. Don't touch it during the run. Check `device/driver/screenshots/` and inspect the tree with `adb exec-out uiautomator dump /dev/tty`.
   - **Only `source_provenance` is BLOCKED:** Karmi had uncommitted changes, possibly made during the run. Commit and rerun.
   - **Usage goldens fail with times like "5:30 AM":** the baselines render in UTC. `./test unit` runs goldens with `TZ=UTC`; do the same when running `flutter test --tags golden` by hand.
   - **Rollback FAIL:** the probe prints its failing check. `migration_chain_round_trip: false` includes the last alembic error line. Reproduce from the Karmi root with `PYTHONPATH=src DAILY_AGENT_ENVIRONMENT=test DAILY_AGENT_DATABASE_URL=<disposable PostgreSQL URL> .venv/bin/python ../Parakh/scripts/migration_rollback.py`. SQLite cannot run below `c9d4e6f2b1a5` by design.
8. **Cross-system contract rejects:** check the JSON schema/version and the exact two SHAs. Karmi's valid executed decisions use `karmi/fake-economy`; Parakh's signed synthetic demo uses `sim/*`, which real Karmi must reject. A fixture-signed Karmi-action bundle can prove SHADOW mechanics but is not a Parakh-verified production policy. Never bypass a verifier/approved cost limit or activate the bundle to make the test green.
9. **Performance/production check blocked:** local latency numbers do not establish a production threshold. Approved budgets, real auth, provider/payment/channel eligibility, migration restore/rollback and HTTPS/telemetry deployment evidence must be reviewed separately. Missing facts stay BLOCKED; no automation converts TESTING to PRODUCTION.
10. **Suspected leaked secret in evidence:** stop sharing that artifact, rotate the credential via its owner, and inspect the private run locally without copying raw lines into issues. Logs deliberately remove credential-bearing lines. The tracked-file scanner reports only path and signature class, not secret contents.

Each failed gate keeps its own evidence; diagnose and rerun just that stage before attempting `full`/`production-check` again. Preserve other users' working files and previous runs; never `git clean`, reset or delete shared services as a shortcut.
