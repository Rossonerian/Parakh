# Karmi ↔ Parakh offline exchange (version 1)

`telemetry_batch_v1.schema.json` describes sanitized `TelemetryBatchV1` files. A compatible Karmi producer must export batch ID, producer/version, feature schema, model registry, routing context, exactly one executed decision per run, optional shadow decisions, logged selection probability, attempts/tool/validation events, outcomes and sanitized feedback. Parakh's strict parser (`model_lab/telemetry/schema.py`) is authoritative: malformed or privacy-flagged runs remain quarantined with per-record reasons; a repeated batch ID with identical checksum is idempotent, while altered contents are rejected. The supplied `fixtures/telemetry_batch_v1.sample.json` and `model_lab.telemetry.synthetic` are *simulated*, not production logs. Do not include raw authorization headers, secrets, credentials or prohibited PII; Parakh checks again but cannot promise perfect anonymization.

`policy_bundle_v1.schema.json` describes each JSON file in `PolicyBundleV1`. `artifact export` emits `manifest.json`, `routing_policy.json`, `feature_schema.json`, `eligibility_constraints.json`, `evaluation.json`, `provenance.json`, optionally `harness/prompts.json` and `harness/recovery_policy.json`, plus `checksums.json` and detached `signature.sig`. Files use canonical JSON; checksums cover the payload; Ed25519 signs the exact checksums bytes. The verifier must pass before a named operator can approve and export. The receiving service must supply an independently trusted public key, check signature, checksums and file set, feature schema/model registry/minimum version compatibility, and enforce its own eligibility and budget rules. Never trust the public key merely because it appears in the signed bundle.

`karmi_reference/loader.py` is a standalone compatibility fixture, **not** the actual kashyep-karmi application. It loads a validated candidate only into a shadow slot; Karmi's active router is not modified. Real Karmi deployment or telemetry exchange requires its own integration, operator approvals and shadow observations. Promotion after Parakh `EXPORTED` belongs to Karmi (RECEIVED → STAGED → SHADOW → CANARY → PRODUCTION); Parakh never supplies a production mutation endpoint. The reference loader is not a substitute for a real Karmi staging test.

Karmi's side lives on `Kashyep/Karmi` branch `parakh-shadow-integration` (commits `6f2bb36`..`84e49ad`; local, not pushed or merged; base `62072fc`). Each message run records a feature-only routing context and its executed static decision (`karmi-static-v1`, `selection_probability` 1.0, no exploration); `karmi-parakh export-telemetry` writes deterministic TelemetryBatchV1 windows (costs in synthetic micro-units with currency `XTS`, so Parakh does not USD-normalize them). `karmi-parakh receive-bundle/stage/shadow/retire` verifies bundles with a typed port of `karmi_reference/loader.py` against configured trusted keys, stores a read-only copy and records the SHADOW bundle's own decisions next to the live one; CANARY/PRODUCTION are refused. `fixtures/karmi_export_telemetry_batch_v1.json` is a batch captured from that exporter after a bundle entered SHADOW, and `tests/test_optimization_foundation.py` imports it with zero quarantine. Verified locally on synthetic traffic through Karmi's real HTTP path: Karmi export → Parakh import (idempotent) → reward → dataset → LinUCB → OPE; Karmi SHADOW → next export → Parakh import with shadow disagreement. Not verified: Parakh cannot *verify/export* a bundle over Karmi's real actions (`karmi/fake-economy`, `typesafe/system-one`) until an authorized `pilot run --allow-paid` provides 60-case benchmark evidence for them, so the shadow bundle in that cycle was Karmi-test-signed, not a Parakh export. Static logging gives OPE no support for alternative actions; Karmi has no user feedback signals yet; no Karmi staging/production deployment, Docker integration run or real user telemetry was observed.

Contract version IDs and feature/reward/schema registry constants are in `model_lab/schema_registry.py`. Breaking contract changes require new versioned schemas and a Karmi compatibility check; do not silently reinterpret v1 fields. Python ≥3.11 is the tested repository runtime; the versioned JSON transfer contains no pickle, Python objects or executable code.
